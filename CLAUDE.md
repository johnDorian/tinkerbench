# tinkerbench

Agent-driven workbenches for hobby electronics and 3D printing: three independent Go apps, each with its own `go.mod`, Dockerfile, Taskfile and Svelte UI in `web/` (embedded from `web/dist`, built in the Docker image). See [README.md](README.md) for the overview and each app's README for details.

The repo is meant to become public: keep personal details (home network addresses, host names, paths, names) out of code, defaults, tests and docs. Deployment-specific values come from environment variables; defaults point at `localhost`.

Root [Taskfile.yml](Taskfile.yml) includes `openscad:`, `fritzing:`, `orcaslicer:`; `task test` runs all Go tests. [docker-compose.yaml](docker-compose.yaml) is a standalone demo on localhost; real deployments use their own compose file and build from this folder.

## Apps

- **[openscad_viewer/](openscad_viewer/)**: OpenSCAD workbench. Models name their pieces with `part("name")` and `feature("name", [x, y, z])` from `use <workbench.scad>`; the server renders each part separately (`GET .../parts`, `.../parts/<name>.stl`) and comments can be anchored on a face, edge or point of a part (`list_parts`, `add_comment` with `anchor`). An agent writes/renders `.scad` projects over MCP (`/mcp`) while the UI shows code and a three.js model live via SSE; the person can comment/suggest on code lines (`comments.json`, re-anchored on every save) and the agent works through them with the comment MCP tools. Go stdlib only; an OpenSCAD development snapshot (AppImage pinned by `OPENSCAD_SNAPSHOT` in the Dockerfile, run with `OPENSCAD_ARGS=--backend=manifold`, far faster than Debian's 2021.01 CGAL build) + xvfb + BOSL2 in the image; plain files (with per-save history) in `DATA_DIR`, port 8020. `SLICER_URL` shows the "Slice" button (opens `<SLICER_URL>/?import=<project>`). Tasks: `task openscad:test`, `task openscad:run`, `task openscad:web:dev`.
  - **Copying a real part**: images of the part are uploaded per project into `images/` (not versioned, 32 MB each, `?w=` serves a shrunk copy) via the UI's Images tab or `upload_image`; `measure_part` turns a scan or photo into millimetres (overall size, the steps along the outline, a circle fit for a round end, an OpenSCAD variable block, plus an annotated overlay to check). It only sees the silhouette: anything in Z must be asked for with a caliper, which is what the `scad-copy-part` skill is for.
  - The measuring code ([internal/imaging/](openscad_viewer/internal/imaging/), [internal/measure/](openscad_viewer/internal/measure/)) is a stdlib port of a Python/OpenCV tool, validated against it digit-for-digit. **Don't add gocv/OpenCV**: it would force CGO and ~300 MB onto the image.
  - **Printability**: before adding any feature that starts above the bed (lips, ledges, hooks, collars) and before calling a model done, follow the `scad-printability` skill: every such feature needs an `assert` proving it overlaps what holds it up.
  - When `openscad` is a snap it has a private `/tmp`, so run the tests as `TMPDIR=$HOME/scadtest task openscad:test` or `TestRender` fails.
- **[fritzing/](fritzing/)**: Fritzing workbench, same shape as openscad_viewer. An agent builds sketches over MCP (`/mcp`) while the UI shows the breadboard/schematic/PCB SVGs live. Go server (pure-Go SQLite for the parts library) runs Debian's Fritzing 0.9.6 as a subprocess (`Fritzing -svg <folder>`, offscreen Qt; the Debian `fritzing` wrapper script drops arguments, so the image calls the real binary under a prepared HOME). Search reads Fritzing's `parts.db` plus a separate library of parts imported one `.fzpz` at a time (`import_part`, `DATA_DIR/userparts`, bundled into the `.fzz` when a sketch uses them); `internal/sketch` edits the `.fz` XML (add/move/connect/remove, pin positions from the part SVGs). Plain files in `DATA_DIR`, port 8030. Tasks: `task fritzing:test`, `task fritzing:docker:run`, `task fritzing:web:dev`. Tests need `FRITZING_TEST_DATA` (see its README).
- **[orcaslicer/](orcaslicer/)**: slicer front end. Import an STL from the OpenSCAD workbench (`OPENSCAD_URL`) or upload one, place it on a three.js bed, pick OrcaSlicer system presets plus a few overrides, slice, print via Moonraker (`PRINTER_URL`, upload with `print=true`; refused while the printer is busy or the slice is stale). Default presets are for an Anycubic Kobra 3 (`DEFAULT_*`). Go stdlib, plain files in `DATA_DIR`, OrcaSlicer 2.4.2 AppImage extracted into the image (debian:trixie, the AppImage needs glibc 2.39), CLI run headless with `--arrange 0`; the backend bakes positions into a 3MF it writes itself (`--export-3mf` crashes headless) and flattens presets with `"from": "system"` (with `User` Orca calls them incompatible). Runs on non-AVX2 CPUs. MCP at `/mcp` (print/cancel need `confirm: true`), port 8050. Tasks: `task orcaslicer:test` (real-CLI tests need `ORCA_TEST_BIN=<extracted AppRun>`), `task orcaslicer:run`, `task orcaslicer:web:dev`.

## Subagents

Use the agents in [.claude/agents/](.claude/agents/) when a task falls mainly in their area: `go-app-dev` for Go backends, `svelte-vite-frontend` for the `web/` UIs. Run independent parts in parallel (e.g. backend and frontend of one feature); do small changes inline.
